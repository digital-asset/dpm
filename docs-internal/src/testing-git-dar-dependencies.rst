Testing Git DAR dependencies with local DPM and damlc builds
=============================================================

This guide exercises Git-hosted DARs in both ``dependencies`` and
``data-dependencies`` using:

* a locally built ``dpm-dev``;
* a locally built ``damlc``; and
* a Daml consumer project.

The tester supplies all repository and project paths through the variables
defined below.

The important integration boundary
----------------------------------

``damlc`` does not fetch or understand ``git:`` dependency locations by
itself. DPM:

1. parses the Git location in ``daml.yaml``;
2. downloads the DAR into the DPM cache;
3. pins mutable Git refs to commit SHAs where applicable;
4. writes the resolved local DAR paths to a resolution file; and
5. starts ``damlc`` with ``DPM_RESOLUTION_FILE`` pointing at that file.

Consequently, the end-to-end test must use the custom DPM binary to launch the
custom compiler. A separate direct-``damlc`` test can reuse a resolution file
generated by DPM to isolate compiler behavior from launcher behavior.

Test inputs
-----------

This guide uses three public inputs:

* Repository DAR: ``github.com/gonzamontiel/test-daml-hello``. Its
  ``dist/test-daml-component-0.0.1.dar`` exposes ``Hello.greeting``.
* Large repository DAR:
  ``git:github.com/canton-network/splice.git#0.6.10?path=daml/dars/splice-amulet-0.1.19.dar``.
* GitHub release:
  ``github.com/Moonsong-Labs/daml-finance``, release
  ``test-release-0.0.6``. The release has multiple DAR assets, including
  ``daml-finance-interface-types-common.dar``.
* Non-GitHub repository DAR:
  ``git:gitlab.com/calvogenerico/daml-temp-coso#main?path=Coso-0.0.1.dar``.

Prerequisites
-------------

* Go and the DPM repository's normal development dependencies.
* Nix, Bazel, and the Daml SDK development environment.
* ``git`` and network access to GitHub.
* A writable ``DPM_HOME``. The SDK's ``dpm-sdk-head`` script installs the head
  compiler under ``$HOME/.dpm``.
* The test project must use ``sdk-version: 0.0.0``.

Set reusable paths. Replace each ``<...>`` placeholder before continuing:

.. code:: bash

   export DPM_REPO="<path-to-dpm-repository>"
   export DAML_SDK_REPO="<path-to-daml-sdk-repository>"
   export TEST_APP="<path-to-consumer-test-application>"
   export DPM_HOME="$HOME/.dpm"
   export RESOLUTION_FILE="$(mktemp -t consumer-app-resolution.XXXXXX)"
   export PATH="$DPM_REPO/target:$DPM_HOME/bin:$PATH"

The SDK's ``dpm-sdk-head`` script currently installs into ``$HOME/.dpm``
directly, so this test deliberately uses that value instead of an isolated
``DPM_HOME``.

Before starting, preserve any uncommitted ``daml.yaml`` changes in the test
application. ``dpm-dev install`` and ``dpm-dev update`` intentionally rewrite
mutable Git refs and release entries.

Phase 1: build and verify the custom DPM
----------------------------------------

Build a single development binary:

.. code:: bash

   cd "$DPM_REPO"
   mkdir -p target
   go build -o target/dpm-dev ./cmd/dpm
   dpm-dev --version
   go test -v ./...

For a release-shaped local build, run ``make local-build`` instead. That adds
version metadata and writes platform-specific artifacts under ``dist/``.

Do not replace ``$DPM_HOME/bin/dpm`` for this test. The development binary is
named ``dpm-dev`` and lives under the DPM repository's ``target`` directory,
which is added to ``PATH`` before ``$DPM_HOME/bin``. It therefore cannot
collide with the installed ``dpm``. Invoking ``dpm-dev``
explicitly proves that the source-tree binary handled each operation.

Phase 2: build and install local damlc
--------------------------------------

Enter the SDK development environment and build the DPM-installable compiler
component:

.. code:: bash

   cd "$DAML_SDK_REPO"
   eval "$("$DAML_SDK_REPO/dev-env/bin/dade" assist)"
   bazel build //compiler/damlc:damlc-oci
   "$DAML_SDK_REPO/dev-env/bin/dpm-sdk-head" --damlc

Use the absolute, variable-qualified path for ``dpm-sdk-head``. The script
compares its invocation path with the absolute Bazel workspace path, so
invoking it as ``./dev-env/bin/dpm-sdk-head`` can fail the repository-root
check even when the current directory is correct.

The final command installs the component as version ``0.0.0`` under
``$DPM_HOME/cache/components/damlc/0.0.0``. This guide uses ``dpm-dev`` to
launch that compiler component; it does not use or replace an installed DPM
executable.

Confirm the compiler independently:

.. code:: bash

   DPM_SDK_VERSION=0.0.0 dpm-dev damlc --version
   test -x "$DPM_HOME/cache/components/damlc/0.0.0/damlc-dist-dpm/damlc"

Do not use ``bazel run damlc -- build``: that execution mode lacks resources
required by ``ghc-pkg``. Install the packaged head compiler with
``dpm-sdk-head --damlc``, then run project builds through ``dpm-dev build`` or
the installed compiler binary. ``bazel run damlc -- compile`` remains useful
for single-file compiler development.

Phase 3: link the custom DPM to the custom damlc
------------------------------------------------

The SDK head install registers ``damlc`` in the local ``0.0.0`` SDK assembly.
Select that assembly while invoking the custom DPM:

.. code:: bash

   cd "$TEST_APP"
   export DPM_SDK_VERSION=0.0.0
   dpm-dev damlc --version
   dpm-dev --help

Expected result:

* ``damlc`` appears as a DPM command;
* the reported compiler is the head build; and
* ``build``, ``test``, ``inspect-dar``, and ``validate-dar`` appear as
  compiler-backed commands.

If DPM cannot find the assembly, verify:

.. code:: bash

   test -f "$DPM_HOME/cache/sdk/open-source/0.0.0.yaml"
   dpm-dev sdk-version

For an explicit assembly override, use:

.. code:: bash

   export DPM_ASSEMBLY="$DPM_HOME/cache/sdk/open-source/0.0.0.yaml"

Phase 4: establish a clean baseline
-----------------------------------

The test app already imports ``Hello`` and asserts that
``Hello.greeting == "Hello, World"``. Start from a clean project build cache:

.. code:: bash

   cd "$TEST_APP"
   rm -rf .daml

Use this minimal baseline before adding remote DARs:

.. code:: yaml

   sdk-version: 0.0.0
   name: consumer-app
   source: daml
   version: 0.0.1

   dependencies:
     - daml-prim
     - daml-stdlib
     - daml-script

   data-dependencies: []

Then install SDK libraries and attempt a build:

.. code:: bash

   dpm-dev install
   dpm-dev build

The build is expected to fail because ``Main.daml`` and
``ComponentImportTest.daml`` still import ``Hello``, and no DAR that
provides that module is declared yet. That confirms a later success comes
from the remote DAR and not a stale package database.

Phase 5: repository DAR in ``dependencies``
-------------------------------------------

Add the public ``test-daml-hello`` DAR using its branch:

.. code:: bash

   cd "$TEST_APP"
   dpm-dev add dar \
     'git:github.com/gonzamontiel/test-daml-hello.git#master?path=dist/test-daml-component-0.0.1.dar' \
     --dependencies

Alternatively, add the equivalent line manually:

.. code:: yaml

   dependencies:
     - daml-prim
     - daml-stdlib
     - daml-script
     - git:github.com/gonzamontiel/test-daml-hello.git#master?path=dist/test-daml-component-0.0.1.dar

Resolve, build, and test:

.. code:: bash

   dpm-dev install
   dpm-dev resolve -o yaml
   dpm-dev build
   dpm-dev test

Expected result:

* ``install`` rewrites ``#master`` to a 40-character commit SHA;
* the rewritten line remains under ``dependencies``;
* ``resolve`` contains an absolute cached path under
  ``imports.resolved-dependencies``;
* ``.daml/dist/consumer-app-0.0.1.dar`` is produced; and
* ``testComponentGreeting`` passes.

Run the same commands a second time. The warm-cache build should succeed
without cloning the repository again.

Phase 6: repository DAR in ``data-dependencies``
------------------------------------------------

Move the Hello DAR from ``dependencies`` to ``data-dependencies`` without
changing its Git location:

.. code:: yaml

   dependencies:
     - daml-prim
     - daml-stdlib
     - daml-script

   data-dependencies:
     - git:github.com/gonzamontiel/test-daml-hello.git#master?path=dist/test-daml-component-0.0.1.dar

Then run:

.. code:: bash

   rm -rf .daml
   dpm-dev install
   dpm-dev resolve -o yaml
   dpm-dev build
   dpm-dev test

Expected result:

* the ref is pinned in ``data-dependencies``, not moved to ``dependencies``;
* ``resolve`` lists it under ``imports.resolved-data-dependencies``; and
* the imported ``Hello`` module compiles from the reconstructed DALF
  interface.

This test is intentionally stronger than merely checking that a DAR was
downloaded: application source imports and evaluates a symbol from the
data-dependency.

Phase 7: large tagged repository DAR
------------------------------------

Add the Splice Amulet DAR as a data-dependency:

.. code:: bash

   dpm-dev add dar \
     'git:github.com/canton-network/splice.git#0.6.10?path=daml/dars/splice-amulet-0.1.19.dar' \
     --data-dependencies
   dpm-dev install
   dpm-dev resolve -o yaml
   dpm-dev build

Expected result:

* tag ``0.6.10`` is rewritten to its commit SHA;
* the DAR is present in ``resolved-data-dependencies``;
* the custom compiler accepts the downloaded DAR; and
* the consumer DAR builds.

This is primarily a fetch, pinning, and large-repository test. To make it a
compiler API test as well, add a small Daml module that imports one exposed
module from ``splice-amulet`` and refers to one of its public types. Keep that
module with the test fixture so package API changes are reviewed explicitly,
rather than relying on an unstable module name in this generic guide.

Phase 8: one DAR from a GitHub release
--------------------------------------

Test release mode with a small interface DAR:

.. code:: bash

   dpm-dev add dar \
     'git:github.com/Moonsong-Labs/daml-finance?release=test-release-0.0.6&asset=daml-finance-interface-types-common.dar' \
     --data-dependencies
   dpm-dev install
   dpm-dev resolve -o yaml
   dpm-dev build

The dependency can also be written directly:

.. code:: yaml

   data-dependencies:
     - git:github.com/Moonsong-Labs/daml-finance?release=test-release-0.0.6&asset=daml-finance-interface-types-common.dar

Expected result:

* DPM downloads exactly the selected release asset;
* the release entry remains release-based rather than being converted to a
  commit SHA;
* the local path appears in ``resolved-data-dependencies``; and
* the project builds with the local head compiler.

Repeat with ``--dependencies`` to verify that release assets are supported in
both fields. A particular DAR may still be semantically suitable for only one
field; that compiler result is separate from DPM's ability to resolve it.

Phase 9: expand every DAR in a GitHub release
---------------------------------------------

Omitting ``asset`` means all ``.dar`` assets:

.. code:: yaml

   data-dependencies:
     - git:github.com/Moonsong-Labs/daml-finance?release=test-release-0.0.6

Run:

.. code:: bash

   dpm-dev install
   dpm-dev resolve -o yaml

Expected result:

* DPM queries the release and replaces the single entry with one entry per
  ``.dar`` asset;
* non-DAR assets, if any, are ignored;
* every expanded entry keeps ``release=test-release-0.0.6`` and gains an
  ``asset=...dar`` query; and
* every asset resolves to a local cache path.

The umbrella release contains many related packages. Compiling all of them in
one field may reveal duplicate unit IDs, unsupported data-dependencies, or
package graph constraints. Record such compiler failures separately from
release listing/download failures. The expansion and resolution checks are
the DPM acceptance criteria for this phase.

Phase 10: invoke damlc directly with DPM's resolution
-----------------------------------------------------

This phase isolates the compiler while retaining DPM's Git resolution. First
write a stable resolution file:

.. code:: bash

   cd "$TEST_APP"
   dpm-dev resolve -o yaml > "$RESOLUTION_FILE"
   export DPM_RESOLUTION_FILE="$RESOLUTION_FILE"
   export DPM_SDK_VERSION=0.0.0
   export DAMLC_UNDER_TEST="$DPM_HOME/cache/components/damlc/0.0.0/damlc-dist-dpm/damlc"
   "$DAMLC_UNDER_TEST" build --package-root "$TEST_APP"
   "$DAMLC_UNDER_TEST" test "$TEST_APP/daml/ComponentImportTest.daml"

Expected result: direct ``damlc`` consumes the local paths from
``DPM_RESOLUTION_FILE`` and produces the same result as
``dpm-dev build``.

As a negative control, unset the file and clean the project cache:

.. code:: bash

   unset DPM_RESOLUTION_FILE
   rm -rf "$TEST_APP/.daml"
   "$DAMLC_UNDER_TEST" build --package-root "$TEST_APP"

With ``git:`` lines still in ``daml.yaml``, this must not be treated as a
successful remote-dependency build. Restore ``DPM_RESOLUTION_FILE`` before
continuing.

Phase 11: update and reproducibility behavior
---------------------------------------------

Verify pinned state:

.. code:: bash

   dpm-dev update --check

Then replace one pinned repository ref with ``master`` or ``0.6.10`` and run:

.. code:: bash

   dpm-dev update --check
   dpm-dev update
   dpm-dev update --check

Expected result:

* the first check rejects an unpinned or missing Git dependency;
* ``update`` fetches it and writes a commit SHA; and
* the final check succeeds.

Release dependencies do not have commit pins; their release tag and asset
name are their declared identity.

Phase 12: repository DAR from a non-GitHub host
-----------------------------------------------

The ``#<ref>?path=…`` form is host-agnostic, so this phase guards against
GitHub-specific assumptions creeping back into parsing, canonicalization, or
pinning. Use the GitLab fixture:

.. code:: bash

   dpm-dev add dar \
     'git:gitlab.com/calvogenerico/daml-temp-coso#main?path=Coso-0.0.1.dar' \
     --data-dependencies
   dpm-dev install
   dpm-dev resolve -o yaml
   dpm-dev build

Expected result:

* ``add`` writes the line to ``daml.yaml`` unchanged apart from canonicalization;
* ``install`` accepts that line and pins ``#main`` to a commit SHA;
* the cached DAR lands under ``$DPM_HOME/cache/git/gitlab.com/...``; and
* a second ``install`` is a no-op rather than rewriting the line again.

The final point matters most. ``add`` and ``install`` normalize dependency lines
through different call paths, so a line that only one of them accepts produces a
``daml.yaml`` that the other rejects.

Also paste a URL straight from the GitLab web UI, which uses a ``/-/blob/``
separator and permits nested groups:

.. code:: bash

   dpm-dev add dar \
     'https://gitlab.com/calvogenerico/daml-temp-coso/-/blob/main/Coso-0.0.1.dar' \
     --data-dependencies

This must yield the same canonical line as the explicit ``git:`` form above.

Negative test matrix
--------------------

Run each case independently and require a non-zero exit status with a useful
error:

.. list-table::
   :header-rows: 1
   :widths: 35 35 30

   * - Input
     - Operation
     - Expected failure
   * - Missing ``?path=`` on a repository dependency
     - ``dpm-dev install``
     - Path is required
   * - Path that does not end in ``.dar``
     - ``dpm-dev install``
     - Invalid DAR path
   * - Nonexistent repository file
     - ``dpm-dev install``
     - File is absent at the selected ref
   * - Nonexistent release tag
     - ``dpm-dev install``
     - GitHub release is not found
   * - Nonexistent release asset
     - ``dpm-dev install``
     - Named asset is not found
   * - ``?release=`` on a non-GitHub host
     - ``dpm-dev install``
     - Releases are github.com only, naming the ``?path=`` alternative
   * - ``git:ssh://...``
     - Parse or install
     - SSH clone URL is rejected
   * - Raw ``https://...dar`` dependency
     - Parse or install
     - HTTP dependencies are not supported
   * - Undefined environment variable in ``daml.yaml``
     - Any DPM resolution
     - Configuration expansion fails

Also test a network-disabled warm-cache build after all refs are pinned. It
should demonstrate whether the intended offline path is complete. Do not
confuse a successful ``.daml`` incremental build with a successful DPM cache
lookup: remove ``.daml`` while retaining ``$DPM_HOME/cache/git``.

Evidence to collect
-------------------

For each phase, save:

* the exact ``daml.yaml`` before and after the operation;
* command, exit status, and relevant log output;
* ``dpm-dev resolve -o yaml`` output;
* whether the run used a cold or warm DPM cache;
* the resulting ``.daml/dist/consumer-app-0.0.1.dar`` checksum;
* the custom DPM and damlc version output; and
* whether the dependency was a full dependency or data-dependency.

A compact result record is:

.. code:: text

   Case:
   DPM commit/version:
   damlc commit/version:
   Dependency syntax:
   Field: dependencies | data-dependencies
   Cache: cold | warm
   Expected:
   Actual:
   Resolution entry:
   daml.yaml rewrite:
   Output DAR SHA-256:
   Status: PASS | FAIL

Cleanup and restoration
-----------------------

Remove test-generated compiler state:

.. code:: bash

   rm -rf "$TEST_APP/.daml"
   rm -f "$RESOLUTION_FILE"
   unset DPM_RESOLUTION_FILE DPM_ASSEMBLY DPM_SDK_VERSION

Restore the test application's original ``daml.yaml`` after completing the
matrix. Keep pinned SHAs only when the fixture is intentionally being updated.
Avoid deleting all of ``$DPM_HOME``: it may contain other installed SDKs and
components.

Acceptance criteria
-------------------

The feature passes when:

1. the custom DPM resolves repository files and release assets in both
   dependency fields;
2. branch and tag refs for repository files are pinned to commit SHAs in the
   original field;
3. release-without-asset expands to all DAR assets;
4. ``dpm-dev resolve`` places each DAR in the matching resolved field;
5. the custom DPM launches the locally built compiler from SDK ``0.0.0``;
6. direct ``damlc`` produces the same result when given DPM's resolution file;
7. the Hello compile-and-script assertion passes for both dependency fields;
8. cold-cache and warm-cache behavior is distinguishable and repeatable; and
9. malformed, unsupported, and missing locations fail clearly.
